## 各种工具的关系

- LLM：大模型，Agent 的大脑

- Agent Tools：提供给 Agent 调用的函数或者API服务

- AI Agent：**Agent 是一个使用 LLM 来决定应用程序控制流的系统**，其负责在**模型、工具和用户**之间的通信。（**控制流**指的是**Agent 决定如何执行任务、调用什么工具、何时调用工具、以及如何根据环境反馈调整行动的逻辑流程**）

- System Prompt：可以告诉AI有哪些工具可以调用，返回需要调用的工具的格式（以自然语言定义）。**但AI仍然可能回答格式不正确，因为AI是一个概率模型，所以需要不断重试（比如cline)**。

- User Prompt

- Function Calling：是一种函数调用，只不过对以自然语言定义的“AI有哪些工具可以调用，返回需要调用的工具的格式”**标准化**。每个 **Tool 的描述都用一个JSON对象**定义：

```
 {

 	"name" :"list_files",
 	"desc"："……",
 	"params:{
 		#参数名：类型
 	}
 }
```

- [MCP（官网链接）](https://github.com/modelcontextprotocol/python-sdk/blob/main/examples/clients/simple-chatbot/mcp_simple_chatbot/main.py#L283)：**MCP（Model Context Protocol，模型上下文协议）** 是由 Anthropic 推出的开放标准，**它为大语言模型与外部系统（工具、数据、API）提供统一的连接接口**；本质上MCP就是对大模型进行function call的调用进行了一层封装。

 MCP规定了MCP Server如何与MCP Client通信，以及MCP Server需要提供哪些接口，比如：MCP Server中有哪些Tool，其功能描述，需要的参数、参数格式、返回格式等等接口。

 MCP协议明确了Server和Client的职责，使得系统架构清晰可扩展：

 - **MCP Server**：作为**能力提供者**，让AI访问外部世界，**负责封装对具体资源（如数据库、API、文件系统）的访问逻辑，并将其以“工具（Tools）”、“资源（Resources）”和“提示模板（Prompts）”三种形式暴露出来。**其中 server 可分为两种`local server（本地服务）` 和 `remote server（远程服务）` 。

 - **MCP Client**：为 **Agent**，嵌入在 AI 应用程序（如Claude Desktop、Cursor）中。**它负责向Server获取可用工具列表，并根据大模型的决策，代为调用相应的工具，最后将结果返回给模型。**

 MCP协议支持两种主要的通信机制，以适应不同的部署场景：

 - **STDIO（标准输入输出）**：用于**本地通信**。Client将Server作为子进程启动，通过标准的输入输出流交换数据。这种方式延迟低、安全性好，适合访问本地文件、数据库等。

 - **SSE（基于HTTP的服务器发送事件）**：用于**远程通信**。Client通过HTTP与远程部署的Server进行长连接通信。这种方式适合调用云端API或需要分布式部署的服务。

 MCP在MCP Server和MCP Client之间最根本的作用是**解耦与赋能**。

## 0 Agent

AI Agent（智能体）的核心能力可以概括为四个关键方面：

- **感知（Perception）**
- **规划（Planning）**
- **行动（Action）**
- **记忆（Memory）**

它们共同构成了 Agent 能够自主理解、决策和执行任务的闭环系统。

下面这个表格汇总了这四大核心能力及其关键技术和意义，方便你快速了解：

| 核心能力 | 关键技术与方法 | 意义与价值 |
| :----------- | :------------------------------------- | :---------------------------------------------- |
| **感知能力** | 多模态融合 (GPT-4V, GPT-4o)、环境解析 | 为复杂任务提供基础数据支持，使 Agent 能“看”和“听” |
| **规划能力** | 思维链 (CoT)、树状思考 (ToT)、动态推理 | Agent 从“执行者”升级为“决策者”的核心标志 |
| **行动能力** | API调用、MCP协议、浏览器/屏幕操控 | 连接数字与物理世界，实现任务落地 |
| **记忆能力** | RAG检索增强、向量数据库、分层记忆管理 | 实现个性化服务与持续学习的基础 |

###  核心能力详解

1. **感知能力 (Perception)**：这是 Agent 与外界交互的基础。它通过多模态输入（文本、图像、语音、传感器数据等）来理解和解析环境及用户意图。例如，GPT-4o这样的模型能直接理解图片中的信息、识别语音中的语气语调。

2. **规划能力 (Planning)**：这是 Agent 的“大脑”或“思考”过程。它涉及**任务拆解、路径规划和决策**。通过CoT（思维链）、ToT（树状思考）等推理框架，**Agent 能将复杂目标分解为可执行的子任务序列**，并动态调整策略以应对变化。例如，旅行规划 Agent 会自动将“安排旅行”分解为订机票、酒店、排行程等步骤。

3. **行动能力 (Action)**：规划好后，Agent 需要通过行动影响和改变环境。这包括**调用工具（如API、软件）、执行命令或操作物理设备**。标准化的协议如MCP（Model Context Protocol）极大方便了 Agent 安全、高效地调用各类工具。例如，Agent 可以调用搜索引擎API获取实时信息，或通过RPA操作浏览器自动完成订票任务。

4. **记忆能力 (Memory)**：记忆使 Agent 能够**存储和回顾信息**，从而在长时间跨度内保持连贯性，并实现持续学习和个性化。**短期记忆**维护当前对话或任务的上下文，**长期记忆**则通过向量数据库和RAG（检索增强生成）等技术存储历史经验、用户偏好和专业知识，减少“幻觉”。

###  运作机制与架构

这些能力并非孤立，而是在 **“感知-规划-行动”循环（如ReAct框架）** 中协同工作：
* **感知**环境与用户输入
* **规划**下一步行动（可能结合记忆中的信息）
* **执行**行动并观察结果
* 根据结果**更新记忆**并进入下一循环

另一种常见架构是 **“规划-执行”模式（ReWoo框架）**，即先制定完整计划再逐步执行，适合复杂任务。

### 什么是智能体Agent:

**Agent 是一个使用 LLM 来决定应用程序控制流的系统**。**决定应用程序控制流**指的是**Agent 可以规划如何执行任务、调用什么工具、何时调用工具、以及如何根据环境反馈调整行动的逻辑流程**。**概括性地说，智能体是一种能够自主感知环境并根据感知结果采取行动的程序**。

智能体的核心范式：

- Agent（智能体）= Planning（规划）+ Tool Use（工具使用）+Reflection（大模型反思） + Memory（记忆）

**概括性地说，智能体是一种能够自主感知环境并根据感知结果采取行动的程序**。

以感知序列为输入，以动作作为输出的函数。它可以以软件形式（如聊天机器人、推荐系统）存在，也可以是物理形态的机器（如自动驾驶汽车、机器人）。其“感知-决策-行动”闭环需要两类核心存储能力：Memory和Knowledge。

基本特性：

- 自主性：能够在没有外部干预的情况下做出决策。
- 交互性：能够与环境交换信息。
- 适应性：根据环境变化调整自身行为。
- 目的性：所有行为都以实现特定目标为导向。

## 1 Agent 运行模式（范式）

其“感知-决策-行动”闭环需要两类核心存储能力：Memory和Knowledge。

### 1.1 ReAct范式

 REACT: SYNERGIZING REASONING AND ACTING IN LANGUAGE MODELS

[ReAct论文解读：LLM ReAct范式，在大语言模型中结合推理和动作](https://zhuanlan.zhihu.com/p/624003116)

作者对人类的行为有一个洞察：

> 在人类从事一项需要多个步骤的任务时，而步骤和步骤之间，或者说动作和动作之间，往往会有一个推理过程。

以做一道菜为例，切好菜和打开煤气之间，有一个这样的推理，或者说内心独白：”现在我切好菜了，后面要煮菜了，我需要打开煤气。“在做菜过程中，如果发生意外，发现没有盐时，有这样一个推理：”没有盐了，今天我就用胡椒粉调味“，然后我们就会去拿胡椒粉。

通过这个洞察，作者提出一个方法：

> 让 LLM 把内心独白说出来，然后再根据独白做相应的动作，来提高 LLM 答案的准确性。

![image-20250908112412032]({{ '/assets/learning/25_agent_systems/figure_003.png' | relative_url }})

**ReAct将模型的planning分为Thought和Action两个步骤**，并让它们交替执行，直到得到最终结果：

- Thought（Reason）：对于输入生成分析步骤，解释当前任务的上下文或状态，帮助模型理解下一步行动的逻辑依据。
- Action：基于Reason的结果，生成具体的工具调用请求（如查询搜索引擎、调用API、数据库检索等），将模型的推理转化为行动。
- observation（Feedback）：action工具调用的结果。

注意：其中第一个Throught输入是prompt，后续的Throught输入则是observation，模型基于observation生成的步骤分析。

### 1.2 ReWoo

ReWOO:Decoupling Reasoning from Observations for Efficient Augmented Language Models

REWOO的全称是Reason without Observation，是相对ReAct中的Observation 来说的。它旨在通过以下方式**改进 ReACT** 风格的 Agent 架构：

第一，**通过生成一次性使用的完整工具链来减少token消耗和执行时间**，因为ReACT模式的 Agent 架构需要多次带有冗余前缀的 LLM 调用；

第二，简化微调过程。由于规划数据不依赖于工具的输出，因此可以在不实际调用工具的情况下对模型进行微调。

- Planner：规划器，制定解决请求的plan，**负责将任务分解**并制定包含多个相互关联计划的**任务链** (DAG有向无环图)，每个计划都分配给Worker执行。
- Worker：执行器，根据规划器提供的蓝图，使用外部工具获取更多证据或者其他具体动作。
- Solver：合并器，将所有计划和证据结合起来，总结生成回答，形成对原始目标任务的最终解决方案。

下图是REWOO的原理：

- Planner：规划器，接收来自用户的输入，输出详细的计划Task List，Task List由多个Plan和 Execution（Tool[arguments for tool]）组成；
- Worker：执行器，接收Task List，循环执行Execution完成task；
- Woker将所有任务的执行结果同步给Solver，Solver将所有的Plan和执行结果整合起来，形成最终的答案输出给用户。

### 1.3 ReAct vs ReWOO

| 特性维度 | ReAct (感知-思考-行动) | ReWOO (规划-执行) | 其他“规划-执行”框架 (例如 Plan-and-Execute, OpenManus) |
| :--------------- | :------------------------------------------------------- | :-------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------- |
| **核心逻辑** | 交错进行推理（Think）与行动（Act），并根据观察（Observe）逐步调整 | **解耦推理与观察**：先制定完整计划（Plan），再集中执行（Work），最后整合求解（Solve） | 先由规划模块（Planner/LLM）生成详细的**任务分解和步骤计划**，再由执行模块（Executor/Agent）按步骤执行 |
| **工作流程** | **循环**：Thought → Action → Observation → ... → Answer | **线性**：Planner生成计划 → Worker执行所有步骤 → Solver整合答案 | **线性或动态调整**：规划 → 按步骤执行 → (可选)根据执行结果动态调整后续计划 |
| **Token效率** | 相对较低，每次循环都需携带历史上下文，冗余较多 | **较高**，仅需两次主要 LLM 调用（Planner和Solver），大幅减少重复提示 | 通常优于ReAct，但取决于规划粒度及是否需要动态重规划 |
| **鲁棒性** | 依赖每一步的观察，单步工具失败可能影响后续循环 | **工具失效时更鲁棒**，因全局计划已生成，Solver可尝试基于已有证据推理 | 依赖初始规划的准确性，若规划不切实际或环境变化大，可能影响效果；部分框架支持动态调整以提升鲁棒性 |
| **适用场景** | 环境反馈至关重要的交互式任务 | **工具调用成本高或需批量操作**的任务；追求更高Token效率的场景 | **复杂、多步骤任务**；需要清晰任务分解和执行的场景 |
| **潜在挑战** | Token消耗大，延迟可能较高 | **高度依赖Planner的初始规划能力**，若规划不佳，后续难以补救 | 同样依赖规划模块的能力；不灵活的规划可能无法适应意外情况 |

ReAct方法：当User输入Task后，把上下文Context和可能的样本Example输入到 LLM 中，LLM 会调用一个目标工具Tool，从而生成Observation。由于拆解后的下一次循环也需要调用 LLM，又会基于Observation产生新的Thought，Action，Observation。**如果这个步骤变得很长，就会导致巨大的重复计算和开销。**

ReWOO的方法：计划器Planner把任务进行分解，分解的依据是它们内部哪些用同类Tool，就把它分成同一类。在最开始，依旧是User输入Task，模型把上下文Context和Examplar进行输入。这里与先前有所不同的是，输入到Planner中，进行分解，然后调用各自的工具Tool。在得到了所有的Tool的输出后，生成计划结果Plan和线索，放到Solver进行总结，然后生成回答。这个过程**只调用了两次 LLM**。

## 2 AI agent 经验总结

原文：[2024 What We’ve Learned From A Year of Building with LLMs – Applied LLMs](https://applied-llms.org/)

### 2.1 prompt engineer：

- 结构化输入与输出
- 任务拆分优于聚合，构建简单任务链
- 保持提示词的“单一职责”
- 精心打磨上下文，上下文并非越多越好，需要精炼，多样性

RAG：RAG是为 LLM"注入”新知识性价比最高的方式。其核心是在提问时，先从知识库中检
索相关文档作为上下文，再让模型回答。

- RAG的上限是检索质量。RAG系统的瓶颈在于检索出的文档质量。评估有三个维度：
 - 相关性：内容是否真的和问题相关
 - 信息密度：内容是否简洁精炼，没有噪声
- 混合搜索：向量搜索 + 关键词搜索
 - 向量搜索：理解与匹配语义
 - 关键词搜索（BM25算法）：精确匹配专有名词
- 优先RAG，而不是SFT
- 长上下文窗口不会让RAG过时：RAG与长上下文是互补关系，而非替代关系。“大海捞针”问题：在充满无关信息的超长上下文中，模型的推理能力会下降。RAG负责先找
 到“针”，再让模型分析。

### 2.2 工作流与优化

- 将大任务拆分成“工作流”，多步骤的简单任务组合，远胜于一个包罗万象的复杂提示词。
- 优先使用“确定性”的工作流（针对某一类任务，其工作流程是具体的确定的），完全自主的AI智能体（Agent）还不够可靠，难以在生产环境部署。
- 通过打乱顺序、避免重复、变换提问等方式获得多样化输出。
- Memory缓存：缓存能极大地节省成本、降低延迟，并提升安全性。用户查询时检查缓存是否命中，**能命中直接返回，否则请求 LLM->存入缓存->返回结果**
- 仅在穷尽提示工程技巧后，才考虑成本高昂的微调。

### 2.3 评估与监控

- 从最简单的单元测试开始
- “LLM 作评委”可用但非万能，需谨慎使用。
- 用“实习生测试”判断任务对 LLM 的合理性。
- 警惕过度优化单一指标，避免损害整体性能。
- 将人工标注任务简化为“是/否”或“A/B对比”
- 好的评估方法可以直接用作线上的实时护栏。
- 必须用下游护栏拦截 LLM 的强行回答和幻觉。

### 3.0 为什么需要Memory模块

大语言模型在处理和生成文本方面表现出色，但它们在本身是**无状态（stateless）**的。这意味着**每次与 LLM 的对话交互都是独立的**，**模型本身不会“记住”过去的对话或经验。**大模型在“记忆”主要局限上下文窗口的大小，存在的局限：

- **上下文窗口的限制导致遗忘问题。**LLM 通过一个有限的“上下文窗口”（Context Window）来处理信息。所有输入（包括Prompt和之前的对话片段）都必须塞入这个窗口。一旦信息超出这个窗口，LLM 就“忘记”了它，无法再访问。这导致了所谓的**“遗忘”**问题；
- **无法个性化。**由于不记住特定用户的历史偏好、习惯或之前的互动，LLM 难以提供真正个性化的体验。每次互动都像是第一次见面；
- **长上下文带来的性能和成本影响。推理速度变慢：**LLM 在处理更长的上下文时，需要进行更多的计算来处理和理解所有输入信息。这会导致推理时间增加，响应速度变慢。**模型表现下降：**尽管 LLM 的上下文窗口越来越大，但研究发现，**模型在超长上下文中检索关键信息的能力可能会下降**。**更高的Token**费用：上下文越长，输入的token数量就越多，从而导致每次API调用的成本更高。

**为什么仅扩大上下文窗口还不够？**

近年来，各大模型厂商不断推出具有更长上下文窗口的模型，从128K到甚至千万级Token。然而，这只是“推迟”了问题的发生，并未从根本上解决问题。在实际应用中，扩大上下文窗口面临两大瓶颈：

1. **信息丢失与噪声干扰**：在长达数周或数月的交互中，对话历史不可避免地会超出任何上下文窗口的限制。更重要的是，**对话内容往往是发散的**。用户可能在讨论完饮食偏好后，又进行了数小时关于编程问题的交流。当再次回到食物话题时，关键的“素食”信息可能被埋没在海量的无关代码讨论中，这便是所谓的“大海捞针”问题。
2. **性能与成本的挑战**：处理超长上下文不仅会显著增加模型的推理延迟，还会带来高昂的Token成本。此外，研究表明，LLM 的注意力机制在处理超长序列时会发生退化，模型难以有效利用距离遥远的信息。

因此，我们需要一种更智能的记忆机制，它应能模仿人类的认知过程：选择性地存储重要信息，整合相关概念，并在需要时准确检索。

记忆系统旨在克服 LLM 的局限性，赋予智能体以下核心能力：

- **引入长期记忆：**存储超出 LLM 上下文窗口的信息，实现高效检索和过滤，避免信息遗忘（长期记忆）；是智能体用于**跨会话、跨任务长期保存知识**的记忆形式。长期记忆的实现通常依赖于**外部存储**或**知识库**。
- **持续知识更新：**通过存储与环境和用户的交互经验，实现自我改进和知识更新（长期记忆）；
- **个性化服务：**记录用户偏好和历史互动，提供定制化回应（长期记忆）；

### 3.1 Memory是什么

**Memory是”信息仓库”，存储历史对话、知识和用户偏好**；人类大脑中主要有三种类型的记忆。

`感官记忆`（Sensory memory）、短期记忆（Short-term memory、Working Memory）、长期记忆（Long-term memory）

对于 Agent：

- `感官记忆（Sensory memory）`：原始输入（包括文本、图像或其他形式）

- `短期记忆（Short-term memory）`：智能体维护**当前对话和任务的即时上下文信息**，主要包括：

 - **会话缓冲（Context）记忆**：保留**最近对话历史的滚动窗口**，确保回答上下文相关性；

 - **工作记忆**：存储当前任务的临时信息，如中间结果、变量值等。

 **短期记忆受限于上下文窗口大小**，适用于简单对话和单一任务场景。

- `长期记忆（Long-term memory）`：是智能体用于**跨会话、跨任务长期保存知识**的记忆形式。长期记忆的实现通常依赖于**外部存储**或**知识库**，包括但不限于：

 - **摘要记忆**：将长对话内容压缩为关键摘要存储；
 - **结构化知识库**：使用数据库或知识图谱存储结构化信息；
 - **向量化存储**：通过向量数据库实现基于语义的记忆检索。

 长期记忆使智能体能够**随着时间累积经验和知识，**它特别适用于**知识密集型应用**和**需要长期个性化**的**场景**。

### 3.2 LLM Memory如何保存

文本形式、参数形式为主

1、**文本形式**

- 好处: 易于理解和实现，而且读写速度都很快，便于快速回忆最近的对话。
- 坏处：如果记忆太长，就会占用很多空间，影响处理速度。

文本形式记忆可进一步细分为几种类型：

- 存储完整的交互信息: ReAct
- 最近的交互信息
- 检索到的交互信息和外部知识。

2、**参数形式**

而如果要存储大量知识，或者需要一个稳定可靠的知识库，参数形式可能更有优势。

这种方式更高级。不直接存储文字，而是把记忆转换成模型参数，就像是把知识压缩成精华。

- 好处: 不受文本长度限制，而且存储效率更高。
- 但是，写入时可能需要更多的计算，而且解释起来也不如文本形式直观。

参数形式的记忆则涉及更复杂的技术，比如: fine-tuning、editing：

- 微调：可以帮助模型快速学习特定领域的知识

- 知识编辑则：可以精确地更新或删除某些记忆，避免影响其他无关的知识。

3、**知识图谱（图结构形式）**

使用 LLM 从语料中挖掘实体、关系，组成知识图谱，供下游使用。

LangGraph 提供了对记忆实现的完全控制

- [`State`](https://github.langchain.ac.cn/langgraph/concepts/low_level/#state)：用户定义的模式，指定要保留的记忆的确切结构。
- [`Checkpointer`](https://github.langchain.ac.cn/langgraph/concepts/persistence/#checkpoints)：在会话中跨不同交互的每一步存储状态的机制。
- [`Store`](https://github.langchain.ac.cn/langgraph/concepts/persistence/#memory-store)：跨会话存储用户特定或应用程序级别数据的机制。

### 3.3 LLM Memory 如何工作

记忆操作像 LLM 大脑，三个部分组成：记忆写入、记忆管理和记忆读取。

实际应用中

- 有些系统只模拟人类的短期记忆，通过上下文学习实现，记忆信息直接写在prompt中。

- 而有些系统则采用了hybird memory（混合记忆架构），明确模拟了人类的短期和长期记忆。短期记忆暂时缓冲最近的感知，而长期记忆则随着时间的推移巩固重要信息。

- 记忆格式上，可以自然语言或嵌入向量形式存储。

- 操作方面，Agent 通过记忆阅读、记忆写入和记忆反思三个关键操作与外部环境进行交互。
 - 记忆阅读: 提取有意义的信息, 以增强 Agent 的行动；
 - 记忆写入: 将感知到的环境信息存储在记忆中；
 - 记忆反思: 模拟了人类审视和评估自己的认知、情感和行为过程的能力。

记忆操作像 LLM 大脑，三个部分组成：记忆写入、记忆管理和记忆读取。

- ①记忆写入: LLM 短期记忆, 接收到新信息时(聊天),以特殊编码方式存入"大脑"
 - `MemGPT`: 自我指导是否写入记忆,智能体根据上下文决定是否更新
 - `MemoGPT`: 聊天时做总结, 提取对话片段的主题, 关键词形式保存,便于查找, topic,summary,dialogues

- ②记忆管理: LLM 长期记忆, 整理短期记忆信息;信息归类, 找出最重要的部分,忘掉次要信息,保持大脑的清晰、高效
 - `MemoryBank`: 智能体从对话内容中提炼每日大事记, 同时不断评估，生成个性特征
 - `Voyager`: 智能体根据环境反馈优化记忆
 - `Generative Agents`: 智能体自我反思，获取更高层次的信息. 从事件信息中生成抽象想法
 - `GITM`: 记忆模块中总结多个计划的关键行动, 建立各种情况下的共同参考计划, 提取最重要的行动步骤

- ③记忆读取: 使用 LLM 记忆解决问题
 - `ChatDB`: SQL操作完成记忆阅读

## 4 Agent 系统框架

Agent 框架是实现智能体自主感知、规划和行动的核心工具，主要分为**单智能体（Single-Agent）**和**多智能体（Multi-Agent）**两大类。

AutoGPT单智能体、LangChain多智能体

### 4.1 AutoGPT
定位

AutoGPT 是一个“目标驱动”的自主智能体框架，旨在让AI Agent 能够自主接收高层目标，自动拆解任务、调用工具，并持续执行直到目标完成。

核心特点

- **全自主任务执行**：Agent 可以自主设定子目标、规划步骤、执行任务，无需人类频繁干预。
- **ReAct机制**：采用“思考-行动-观察”循环，每一步都进行推理、决策、执行和反思。
- **记忆管理**：具备短期和长期记忆，支持多轮、多步骤任务的上下文保持。
- **插件化扩展**：支持通过插件机制集成各类工具和API，如搜索、文件操作、代码执行等。
- 内置Debug模式，支持实时状态可视化

工具机制

- **不自带大量工具**：需要用户自行配置或开发插件，工具调用由大模型推理决定，框架负责调度执行。
- **工具选择**：大模型根据任务需求，从已注册的工具列表中自动选择调用。

适用场景

- 需要长期、复杂、多步骤自主决策的任务，如自动化办公、科研助手、市场分析等。
- 强调“端到端自主执行”的场景。

优缺点

- **优点**：高度自主、灵活扩展、适合复杂任务。
- **缺点**：配置复杂、默认工具少、执行过程可能不稳定或陷入循环。
---
### 4.2 LangChain
定位

LangChain 是一个“大模型应用开发框架”，不仅支持 Agent，还提供丰富的工具链、模板和接口，旨在简化大模型应用的开发流程。

核心特点

- **模块化设计**：提供Models、Prompts、Chains、Agents、Memory等模块，支持灵活组合。
- **丰富的内置工具**：内置大量工具和模板，如搜索引擎、文档加载器、数据库连接器等。
- **标准化 Agent 流程**：提供 Agent Executor等标准化执行器，简化 Agent 开发。
- **多模型支持**：兼容OpenAI、Hugging Face、本地模型等多种大模型。
- **同时支持ReAct和Plan-and-Execute两种核心范式**
- 提供Trace Viewer，可回放执行链路

工具机制

- **自带大量工具**：框架内置常用工具，也可自定义工具。
- **工具选择**：Agent 根据任务自动从工具池中选择，支持多工具协同调用。

适用场景

- 快速开发各类大模型应用，如问答机器人、文档分析、智能客服等。
- 需要快速集成、标准化流程的场景。

优缺点

- **优点**：开发效率高、工具丰富、社区活跃、文档完善。
- **缺点**：自主性不如AutoGPT、复杂任务定制性稍弱。
---
### 4.3 BabyAGI
BabyAGI 是一个轻量级、仿生任务驱动的 Agent 框架，专注于“任务生成与执行”的循环，模拟人类任务管理思维。

核心特点

- **任务循环机制**：核心是“任务生成→任务排序→任务执行→结果存储”的循环。
- **简洁高效**：代码结构简单，易于理解和扩展。
- **仿生设计**：模拟人类“待办事项列表”管理方式，适合任务流管理。
- 动态优先级调整算法（DPA）
- **上下文压缩算法**（Context Compression）
- 任务相关性剪枝（Task Relevance Pruning）

工具机制

- **工具依赖外部**：BabyAGI本身不提供复杂工具，通常依赖LangChain或自定义工具完成具体任务。
- **工具调用**：在任务执行阶段，可调用外部工具（如搜索、计算等），但工具管理需自行实现。

适用场景

- 任务流管理、待办事项自动化、简单任务自主执行。
- 教学、研究、轻量级 Agent 原型开发。

优缺点

- **优点**：轻量、易理解、适合任务流管理。
- **缺点**：功能有限、需自行扩展工具、不适合复杂多模态任务。

## 5 上下文工程（Context Engineering）

**上下文工程与记忆系统形成共生关系，共同支撑智能体的认知能力**。记忆系统作为”信息仓库”，存储历史对话、知识和用户偏好；而上下文工程则扮演”智能调度员”，决定从记忆中检索哪些信息及如何组织呈现给 LLM。

上下文工程的核心在于，LLM 的性能和有效性根本上取决于其接收的**上下文**。实现了上下文工程的系统一般包含三类**基础组件**：

1. **上下文检索与生成：** 涵盖Prompt生成和外部知识获取；
2. **上下文处理：** 涉及长序列处理、自我完善和结构化信息集成；
3. **上下文管理：** 关注记忆层次、压缩技术和优化策略。

## 5.1 上下文工程与记忆的关系

上下文工程与记忆系统紧密且共生，都是AI智能体的重要构建手段。一方面，记忆是上下文的“仓库”， 智能体的记忆系统（如历史对话、知识库、用户偏好）是信息存储地，为 LLM 提供潜在上下文。另一方面，上下文工程是记忆的“调度员”和“优化器”，**上下文工程决定从记忆中检索哪些信息及如何检索，确保提取最相关的记忆片段。**

### 5.2 上下文工程在项目中的例子

在一个文档自动化处理生成的 Agent 项目中，我们面临一个关键挑战：输入文档总量超过500页，远超模型的最大Token限制，同时项目对生成内容的召回率和准确率有较高要求。

为解决这一问题，我们实施了以下**上下文工程策略**：

1. **文档分块处理：**将大型文档集合切分为适当大小的chunks，并存储在文件系统中；
2. **摘要生成：**为每个文档块生成精炼的文字摘要，提供内容概览。并生成整个文档的摘要信息；
3. **动态上下文管理：**赋予 Agent 自主选择的能力，使其可以根据任务需求动态调取相关文档块；
4. **上下文优化：**任务完成后自动释放不再需要的上下文，优化资源利用。

这种方法使 Agent 能够在保持高准确率的同时，有效处理超过模型上下文限制的文档集合。

论文没有明确指出具体的向量数据库，但通常这类嵌入向量会存储在支持快速相似性搜索的向量数据库中，如Chroma、Milvus、FAISS等。

当系统接收到一个新的**消息对（如用户提问和AI回答）**时，提取阶段便会启动。为了准确理解当前对话的上下文，系统会结合两种信息源：

- **全局上下文**：从数据库中检索的整个对话的摘要（Summary），提供对话的宏观主题。
- **局部上下文**：最近的几条消息，提供细粒度的即时背景。

这**两种上下文与新消息对共同构成一个完整的提示（Prompt）**，输入给一个 LLM（论文中使用GPT-4o-mini）来执行提取功能。该 LLM 会从最新的交流中**提炼出关键事实（如“用户是素食主义者”），形成一组候选记忆**。

#### 2. 更新阶段：智能管理记忆库

提取出的候选记忆并不会被直接存入数据库，**而是会进入更新阶段，以确保记忆库的一致性和无冗余**。该过程通过一个智能的“工具调用（Tool Call）”机制实现，具体流程如下：

对于每一个候选记忆，系统会：

1. **在向量数据库中检索出语义最相似的已有记忆（可采用余弦相似度）。**
2. **将候选记忆与这些相似记忆一同提交给 LLM。**
3. **LLM 会自主决策执行以下四种操作之一：**

- **ADD**：如果候选记忆是全新的信息，则添加。
- **UPDATE**：如果候选记忆是对现有信息的补充或更新，则进行修改。
- **DELETE**：如果候选记忆与现有信息相矛盾，则删除旧信息。
- **NOOP**：如果候选记忆是重复或无关的，则不执行任何操作。

通过这种方式，Mem0 能够动态维护一个精炼、准确且与时俱进的记忆库。

#### 3.Mem0的记忆管理流程

- 提取阶段：LLM 从对话中提取关键记忆（文本形式），存入数据库时保留原始文本，而非立即转换为向量。
- 更新阶段：检索相似记忆时，系统先将数据库中的文本记忆通过嵌入模型（论文使用 OpenAI的 text-embedding-small-3）转换为向量，再计算与当前提取记忆的向量相似度。
- 优势：这种设计分离了记忆的存储（文本）与检索（向量），既保证了记忆的可读性，又利用了向量搜索的高效性。

 **与纯向量存储方案的对比**：

- 若直接存储向量，需预先为所有记忆生成嵌入，但：

 - 嵌入模型更新成本高：若更换嵌入模型，需重新计算所有记忆的向量。

 - 失去文本上下文：向量无法直接反映记忆的语义细节，调试时需反向解码（可能损失信息）。

- Mem0的选择避免了这些问题，通过“存储文本+动态嵌入”平衡了灵活性与效率

### 6.1.2 Mem0-g：利用图结构深化记忆

![image-20250928151031752]({{ '/assets/learning/25_agent_systems/figure_013.png' | relative_url }})

论文明确指出使用了**Neo4j**作为其底层的图数据库。为了捕捉信息之间更复杂的关系，研究团队还提出了 Mem0 的增强版——**Mem0-g**（g代表graph）。它将记忆存储为知识图谱，其中节点代表实体（如人、地点），边代表它们之间的关系（如“居住在”、“喜欢”）。

**相比于向量数据库，知识图谱能够存储更加复杂的关系、高级的概念和知识，当它和专注于存储事实片段的向量数据库结合时，能够做到互补，使得整个记忆系统更加完备。**

Mem0-g 的核心流程同样分为提取和更新：

- **图提取**：通过一个两阶段的 LLM 流程，首先从文本中识别出关键实体及其类型（如“Alice - Person”），然后生成连接这些实体的关系三元组（如 `(Alice, lives_in, San_Francisco)`）。
- **图更新与冲突解决**：在集成新信息时，Mem0-g 会检测新关系是否与图中已有关系冲突。如果存在冲突，一个基于 LLM 的“更新解析器”会决定是否将旧关系标记为“过时”，而不是直接删除。这种设计保留了信息的时序性，为更复杂的时间推理提供了可能。

通过将结构化的图表示与语义灵活性相结合，Mem0-g 能够支持更高级的推理，尤其是在需要跨越多个互联事实进行推断的场景中。

## 8 OpenClaw

OpenClaw（俗称 “龙虾”）是一个**本地优先、控制与执行解耦**的开源 AI 智能体框架，核心是让大模型从 “回答” 走向 “执行系统操作”。它以**Gateway 为中心**，通过**Lobster 循环**实现感知 - 规划 - 执行 - 反馈闭环，并用沙箱、审批、白名单等多层安全机制保障本地操作安全。

### 8.1 整体架构：四层分层 + 中心枢纽

OpenClaw 采用**四层分层架构**，所有流量与状态都经过**Gateway（网关）** 统一调度，形成 **1 个 Gateway + N 个 Agent** 的中心辐射架构：：

1. 接入层（Channels / Gateway）

- **定位**：系统入口与消息枢纽，所有外部交互必经此处。
- 核心能力：
- 多渠道接入：支持微信、飞书、钉钉、Telegram、CLI、Web 等。
- **消息标准化**：将各平台消息转为内部统一格式（JSON-RPC）。
- 会话管理：维护上下文、隔离多用户 / 多会话状态。
- **路由调度**：将请求分发到对应 Agent 或技能。

2. 大脑层（Agent Runtime）

- **定位**：决策核心，负责 “思考” 与任务规划。
- 核心能力：
- 意图理解：将自然语言转为结构化任务。
- 任务拆解：复杂任务拆分为原子化工具调用序列。
- 模型适配：兼容 GPT-4、Claude、通义千问、Ollama 等。
- 核心循环：**Lobster Loop（龙虾循环）**，实现自主闭环。

3. 执行层（Skills / Tools）

- **定位**：“动手” 能力，执行系统操作与工具调用。
- 核心能力：
- 技能插件：文件操作、浏览器自动化、Shell、API 调用、邮件、表单填写等。
- 沙箱隔离：Docker 容器运行，防止恶意代码影响宿主机。
- **MCP 协议**：统一工具调用标准，兼容外部模型与服务。

4. 记忆层（Memory）

- **定位**：状态与知识持久化，支持跨会话记忆。
- 核心能力：
- **短期记忆**：会话上下文（JSONL），当前对话有效。
- **长期记忆**：`memory.md`/`soul.md`，跨会话持久化。
- **检索增强**：支持 RAG，从本地文档 / 知识库检索信息。

___

#### Gateway 的路由决策

Gateway 的路由决策分为 **4 层优先级**，LLM 仅参与最后一层。

#### 1. 核心路由层（非 LLM）

这是 Gateway 路由的**主力逻辑**，占比 80%+ 的场景：

- **静态规则匹配**：通过预设的「关键词 - 路由映射表」（如 `写代码→CodeAgent`、`查文件→FileSkill`）直接路由，无需调用 LLM，毫秒级响应。
- **会话上下文匹配**：如果当前会话已绑定特定 Agent（如用户之前明确说 “用代码助手处理”），**则直接将请求路由到该 Agent，避免重复决策。**
- **技能白名单匹配**：对已知的原子技能（如 `shell执行`、`浏览器打开`），直接匹配技能 ID 路由，无需 LLM 介入。

#### 2. LLM 兜底层（仅复杂场景）

仅当以上规则都无法匹配时，Gateway 才会调用 LLM 做「智能意图识别」：

- Gateway 向 LLM 发送**精简提示**：包含用户指令、可用 Agent 列表（名称 + 能力描述）、可用技能列表，要求 LLM 输出结构化的路由指令（如 `{"agentId":"SearchAgent","skillId":""}`）。
- LLM 仅返回「路由决策结果」，不参与后续执行，且 Gateway 会对 LLM 输出做格式校验（防止幻觉），若格式错误则降级到默认 Agent。

为什么不直接用 LLM 做路由？

效率问题、稳定性问题（LLM 存在幻觉风险）、资源与成本消耗（大幅增加 Token 消耗和服务器负载）

___

二、核心机制：Lobster Loop（龙虾循环）

这是 OpenClaw 的灵魂，是**ReAct 模式的工程化实现**，分为四步闭环：

1. **Think（思考 / 规划）**

- Agent 接收用户指令 + 上下文 + 可用工具列表，发送给 LLM。
- LLM 输出结构化计划：工具调用序列、参数、执行顺序。

2. **Act（执行）**

- Runtime 解析计划，调用对应 Skill / 工具。
- 所有执行在**Docker 沙箱**中进行，权限受限。

3. **Observe（观察）**

- 收集执行结果、日志、环境状态。
- 将结果回传给 Agent，作为下一步输入。

4. **Reflect（反思 / 迭代）**

- **Agent 评估结果：是否完成目标、是否需要重试、是否调整计划。**
- 若未完成目标，回到**Think**阶段，生成新计划；完成则结束循环。

**典型流程**：

用户指令 → 接入层 → Gateway → Agent（Lobster 循环） → 执行层（沙箱） → 结果 → Gateway → 用户

___

### 8.2 安全机制：六层防护 + 三级审批

OpenClaw 高度重视本地操作安全，设计了**多层防御体系**：

1. 执行审批（三级策略）

- **自动审批**：低风险操作（如读文件）自动放行。
- **人工确认**：中风险（如写文件、执行 Shell）需用户确认。
- **严格禁止**：高风险（如删系统文件、修改配置）默认禁止。
- 支持**三级策略 × 三种模式**组合，灵活控制风险。

2. 沙箱隔离（Docker）

- 所有工具 / 代码在独立容器运行，与宿主机网络、文件系统隔离。
- 可配置容器权限、资源限制、网络访问白名单。

3. 六层防护链

1. 限流器：防止请求洪水。
2. 来源验证：校验渠道与设备合法性。
3. CSP 注入：内容安全策略，防止 XSS。
4. Token 认证：API 密钥与会话令牌校验。
5. 设备配对：仅授权设备可接入。
6. AllowFrom 白名单：仅允许指定 IP / 域名访问。

### 8.3 多智能体（Multi-Agent）架构

**OpenClaw 是明确支持多智能体（Multi-Agent）架构的框架**，而且它的多 Agent 设计非常有特色，不是简单 “多开几个实例”，而是**主从协作 + 任务分发 + 独立沙箱**的结构。

OpenClaw 采用 **1 个 Gateway + N 个 Agent** 的中心辐射架构：

- Gateway（网关）

唯一入口，负责：会话、路由、鉴权、任务分发。

- Agent（智能体）

每个 Agent 是独立的 “大脑”，拥有：

- 独立的 System Prompt
- 独立的上下文记忆
- 独立的技能集（Tools/Skills）
- 独立的执行沙箱
- 独立的思考循环（Lobster Loop）

多个 Agent 可以**同时运行、互不干扰、互相调用**。多 Agent 协作机制（核心）如下：

（1）任务分发模式

Gateway 收到用户指令后：

1. 判断任务类型
2. 分发给**对应专长的 Agent**
3. 或让多个 Agent 并行执行子任务

例如：

- 写代码 → 分给 CodeAgent
- 查资料 → 分给 SearchAgent
- 系统操作 → 分给 SystemAgent

（2）Agent 之间可以互相调用

OpenClaw 支持 Agent 之间通过内部 RPC 通信：

- Agent A 可以请求 Agent B 完成子任务
- 结果自动汇总给主 Agent
- 最终统一回复用户

OpenClaw 中 Agent 之间的内部通信**核心就是基于 JSON-RPC 实现的**—— 具体来说是「JSON-RPC 2.0 + 内部通信协议（ACP）」的组合：JSON-RPC 作为底层消息格式，ACP（Agent Control Protocol）作为上层业务规范，既保证了通信格式的标准化，又适配了多 Agent 协作的业务场景。

（3）独立沙箱隔离

每个 Agent 的工具执行默认跑在**独立 Docker 沙箱**，避免：

- 环境污染
- 权限越权
- 任务互相干扰

这是它比普通多 Agent 框架强的地方。

### 8.4 独立 Docker 沙箱

简单来说：**Agent 进程共享同一个 Gateway/Agent Runtime 容器（或宿主机进程），但每个 Agent 调用的工具，会在独立的临时 Docker 沙箱容器中执行**。

核心逻辑：Agent 进程 vs 工具沙箱容器

1. Agent 进程：共享运行时，不单独占容器

- OpenClaw 的所有 Agent（CodeAgent、FileAgent、SearchAgent 等）本质是**逻辑层面的 “角色 / 配置集”**，而非物理进程 —— 它们共享同一个 Agent Runtime 进程（无论这个进程跑在宿主机还是 Gateway 容器里）。
- 举例：你在 Gateway 中配置了 5 个 Agent，这些 Agent 并不会启动 5 个独立容器，而是在同一个 Runtime 进程中，通过 “配置隔离”（不同的 System Prompt、工具白名单、权限）区分角色。
- 优势：节省资源，避免容器泛滥；Agent 间通信更高效（无需跨容器网络）。

2. 工具沙箱：按需创建临时容器，执行完销毁

当某个 Agent 需要调用工具（如 `shell_exec`、`file_read`）时，OpenClaw 会：

1. **动态创建**：为本次工具调用创建一个**临时 Docker 容器**（基于 OpenClaw 官方沙箱镜像）；
2. **独立隔离**：每个工具调用的沙箱容器都是独立的（即使是同一个 Agent 连续调用工具，也可配置为每次创建新容器）；
3. **执行销毁**：工具执行完成后，沙箱容器默认自动销毁（可配置保留日志）；
4. **资源限制**：每个沙箱容器可单独配置 CPU / 内存限制、网络权限、文件挂载范围。

**动态创建临时 Docker 容器确实会增加工具调用的处理时间**（主要是容器创建 / 启动的开销），这是 “极致隔离” 必然带来的 trade-off（取舍）。但 OpenClaw 针对这个问题做了多层优化，既保留沙箱隔离的安全性，又把性能损耗控制在可接受范围。

### 9.2 并行化

通过并行化，LLM 可以同时处理一个任务：

- LLM 有时可以同时处理一个任务，并以程序化的方式聚合它们的输出。这种工作流，即并行化，体现在两个关键变体中：分块：将任务分解为**并行运行的独立子任务**。投票：多次运行同一任务以获得多样化的输出。
- 何时使用此工作流：当划分的子任务可以并行化以提高速度，或者当需要多个视角或尝试以获得更高置信度的结果时，并行化是有效的。对于具有多个考量因素的复杂任务，如果每个考量因素都由一个单独的 LLM 调用来处理，从而允许专注于每个具体方面，LLM 通常表现得更好。

### 9.3 路由

路由对输入进行分类，并将其引导至后续任务：

- 路由对输入进行分类，并将其引导至一个专门的后续任务。这种工作流允许关注点分离，并构建更专业的提示。没有这种工作流，为一种输入进行优化可能会损害在其他输入上的性能。
- 何时使用此工作流：路由非常适用于复杂任务，其中存在最好分开处理的不同类别，并且分类可以由 LLM 或更传统的分类模型/算法准确处理。

### 9.4 协调器-工作器

通过协调器-工作器，协调器分解任务并将每个子任务委派给工作器。

- 在协调器-工作器工作流中，一个中央 LLM 动态地分解任务，将它们委派给工作器 LLM，并综合它们的结果。

- 何时使用此工作流：此工作流非常适用于您无法预测所需子任务的复杂任务（例如，在编码中，需要更改的文件数量以及每个文件中更改的性质可能取决于任务）。尽管在拓扑上相似，但与并行化的关键区别在于其灵活性——子任务不是预定义的，而是由协调器根据具体输入确定的

 <img src="{{ '/assets/learning/25_agent_systems/figure_014.png' | relative_url }}" alt="image-20251023164827747" style="zoom:50%;" />

由于协调器-工作器工作流很常见，LangGraph **提供了 `Send` API 来支持这一点**。它允许您动态创建工作器节点，并向每个节点发送一个特定的输入。每个工作器都有自己的状态，所有工作器的输出都写入一个对协调器图可访问的*共享状态键*。这使得协调器可以访问所有工作器的输出，并允许它将它们综合成一个最终输出。

### 9.5 评估器-优化器

在评估器-优化器工作流中，一个 LLM 调用生成一个响应，而另一个 LLM 在一个循环中提供评估和反馈

何时使用此工作流：当我们有明确的评估标准，并且迭代改进能提供可衡量的价值时，此工作流尤其有效。两个适合的迹象是，首先，当人类表达他们的反馈时，LLM 的响应可以得到明显改善；其次，LLM 能够提供这样的反馈。这类似于人类作家在创作一份精良文档时可能经历的迭代写作过程。

### 9.6 硬编码

在 Agent（智能体）开发中，**硬编码（Hardcoding）**指的是将特定值、逻辑或行为直接**固定**在代码中，而非通过外部配置、动态学习或环境交互获取。这种做法虽然简单直接，但会降低 Agent 的灵活性、适应性和可维护性。

1. **固定行为策略**

 - **示例**：在规则型 Agent 中，直接编写条件语句（如`if-else`）决定行动，而非通过学习或环境反馈调整。
 - **代码片段**：

```python
def choose_action(state):
    if state "hungry":
        return "eat" # 硬编码行为
    elif state "tired":
        return "sleep"
```

2. **静态知识库**
- **示例**：将知识（如事实、规则）直接嵌入代码，而非从外部数据库或文档动态加载。
- **代码片段**：

```python
      KNOWLEDGE = {
      "Paris": {"capital": "France", "population": 2.148e6}, # 硬编码知识
      "London": {"capital": "UK", "population": 8.982e6}
      }
```

**改进方案：替代硬编码的方法**

1. **动态配置与外部化**

- **方法**：将参数、知识或规则存储在外部文件（如JSON、YAML）或数据库中，通过API动态加载。
- **示例**：

```python
      import json

 with open("config.json") as f:
 config = json.load(f) # 动态加载配置
 KNOWLEDGE = config["knowledge"]
```

2. **机器学习与强化学习**

- **方法**：通过训练让 Agent 学习最优策略，而非手动编写规则。
- **示例**：使用Q-learning算法动态调整行为策略。

| **场景**               | **硬编码实现**                   | **动态实现**                 |
| ---------------------- | -------------------------------- | ---------------------------- |
| **客服 Agent 回答**    | 固定回答模板（如“您的问题是…”）  | 从知识图谱动态检索答案       |
| **游戏NPC行为**        | 预设行为树（如“追击→攻击→撤退”） | 通过强化学习动态选择动作     |
| **工业机器人路径规划** | 固定路径坐标                     | 实时感知障碍物并动态规划路径 |
